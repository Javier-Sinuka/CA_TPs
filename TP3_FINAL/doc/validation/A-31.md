## Verificación con oráculos propios

Cada barrido recorre **563 palabras observables**: PC, dirección imem, halted, 32 registros, 16 latches y 256 pares dirty/dato. Los selectores cambian sin clocks y se comprueba la respuesta combinacional. Los barridos se repiten tras dos clocks con enable=0 y se comparan con el snapshot completo. Los 256 contenidos de imem se cotejan aparte contra la imagen escrita por el arnés.

| Caso del CPU real | Oráculo independiente |
|---|---|
| Reset con enable=0 | PC=0, halted=0, 32 registros cero, 16 latches cero y 256 palabras limpias leídas como cero; imem intacta. |
| Programa de llenado | Palabra n=n+1 para n=0…254; palabra 255=0. Las **256** están dirty, incluida la escritura de cero. x1…x31=`17×índice+1`, x0=0. |
| Pausas en ejecución | Barrido completo cada 37 avances, snapshot estable entre clocks pausados, máscaras de info MEM/WB y flags reservados cero. |
| Escritura de imem durante pausa | Cambiar la palabra no ejecutada 254 a `13579BDF` conserva todo el snapshot del CPU. |
| Segundo reset después de llenar | Dirty y registros se limpian aun detenido por HALT; todos los datos debug vuelven a cero e imem conserva las 256 palabras. |
| SB sobre palabra limpia | Dirección 1 produce palabra 0=`00005A00`, sin recuperar el dato físico anterior. |
| SH sobre palabra limpia | Dirección 510 produce palabra 127=`FFFF0000`, sin conservar bytes bajos del programa anterior. |
| Store de cero | Palabra 128=0 y dirty=1, diferenciada de las palabras limpias. |
| SW desalineado y wrap | Dirección 1023 escribe palabra 255=`0000005A`; dirección 1040 escribe palabra 4=`0000005A`. |
| Loads y memoria limpia | x3=`00005A00`, x4=`FFFF0000`, x5=0, x6=x7=`0000005A`, x8=0 por un load de palabra 126 limpia. |
| PC completo y memoria externa | JAL desde PC 0 a 1032 usa la palabra 2 de imem. x1=123, HALT PC WB=1036 y PC IF=1040. |
| HALT y recuperación | Flags públicos `98`, freeze con enable alto después de detenerse y reset prioritario con enable bajo. |

El segundo programa deja solo cinco palabras dirty (0, 4, 127, 128 y 255); se comprueban también las otras 251 limpias. Los valores distintos en todos los registros y en los índices de memoria permiten detectar pérdida de bits altos del selector.

La variante stub usa exclusivamente sus fórmulas de B-09: PC=`ciclos×4`; xi=`ciclos×256+i` para i>0; latches=`1A000000+(selector×65536)+ciclos`; dirty en 4, 16 y 63 después del primer avance. Se barre tras cada uno de sus 20 avances, se comprueba freeze al llegar a HALT y se resetea con enable=0 sin borrar imem. No se exige que sus patrones sean estado arquitectónico del CPU real.

Los encodings se contrastaron con el ensamblador de B: **40 palabras** del programa de llenado/registros, **14** del programa de stores parciales/loads y **3** del programa de PC alto. Las expectativas de registros y memoria del TB no se generan a partir de las salidas del DUT. Ambas variantes tienen watchdog, límite de avances y `$fatal` ante discrepancias.

## Sensibilidad y límites del cierre

El arnés detectó en copias temporales: índice de acceso dmem truncado a siete bits; índice de datos debug truncado a siete bits; exposición del RAM físico para palabras limpias; dirty no activado en stores de cero; store parcial que mezcla con contenido físico anterior; reset de dirty condicionado por enable; selector de registros truncado a cuatro bits; dirección de instrucciones dividida por cuatro; PC debug truncado a diez bits. Las fuentes originales permanecieron intactas. `+FAIL_FAST` permite terminar en la primera discrepancia.

No se repitió síntesis porque no cambió RTL. La corrida OOC de [A-30](A-30.md) sigue correspondiendo a estas fuentes: 2.872 LUT totales, 1.739 FF y cero latches. No se acredita una nueva corrida de síntesis, timing implementado ni pruebas de placa.

El runner `test` de A ejecuta 30 targets, incluidos los dos usos del mismo top de contrato. No representa la suite completa software/UART/host de B. La elaboración de `system.v` demuestra compatibilidad estructural; la carga por Debug Unit, comandos UART, serialización y comparación de dumps reales se verifican en **A-32**, que es el siguiente issue. A-M08 permanece abierto hasta A-33; su informe de milestone se generará al completar las cuatro issues.
